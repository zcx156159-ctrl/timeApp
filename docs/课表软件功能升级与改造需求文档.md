## 1. 项目背景与目标

### 1.1 背景

现有课表软件已完成第一版：基于 Kotlin Multiplatform + Compose Multiplatform，Android、iOS、
Desktop、Web(Wasm) 四端共用一套代码；具备基础课程管理（增删改、跨节次展示、颜色）、本地持久化、
共享码云同步（自建轻量后端）等能力。

第一版定位为“能用”，在真实使用场景下仍存在明显短板：课程模型过于简单（无学期/周次概念）、
视图单一、无账号体系、云端数据无权限控制、无提醒、无导入导出等。

### 1.2 升级目标

1. **体验升级**：让课程录入更贴近真实教务（学期、周次、单双周、节次时间），视图更直观（日/周视图）。
2. **数据升级**：建立账号体系与真正的云端存储，实现多端可靠同步、多课表管理、导入导出与备份。
3. **协作升级**：共享从“一个裸共享码”演进为“可管理权限的共享/订阅”，支持多人协作。
4. **智能化升级**：提醒、统计、考试安排、空教室查询等增值能力。

### 1.3 范围说明

本文档覆盖功能需求（FR）、非功能需求（NFR）、技术架构改造建议、数据模型演进、后端 API 草案、
迭代里程碑与验收策略。**不含 UI 视觉稿、具体排期承诺与商务内容**。

### 1.4 已确认的产品决策（2026-08-12）

| 决策项 | 结论 |
|--------|------|
| 第一交付版本 | **V1.1（体验版）**，先做学期/周次/节次时间/日视图/Excel 导入/提醒等单机体验升级 |
| 目标用户 | 在校大学生（个人开发者维护，规模可控） |
| 预期用户规模 | **百人级**（按此设计并发与存储，单机宝塔 MySQL 足够） |
| 教务系统对接 | **不做直连**（无公开 API、维护成本高、有合规风险）；采用 **Excel 模板批量导入**（FR-106）作为实际录入路径 |
| 账号登录 | 优先**邮箱/手机号+密码**；**微信登录列 P1，需企业资质**（个人开发者无法开通微信开放平台登录） |
| 后端数据库 | **宝塔 MySQL**（开发期可用 SQLite 快速迭代，生产切 MySQL） |
| iOS 分发 | **不上架 App Store**；TestFlight 内测 + 本地调试；主分发渠道为 Web + 安卓 APK |

### 2.3 已知限制（升级要解决的痛点）

| 编号 | 限制 | 影响 |
|------|------|------|
| L1 | 无学期/周次概念，课程只能“每周都有” | 单双周、起止周、实训周课程无法表达 |
| L2 | 固定 12 节，节次时间写死 | 不同学校作息无法适配 |
| L3 | 无账号体系，共享码即可读写 | 无权限控制、无法找回数据、无法多设备归属 |
| L4 | 同步为整表覆盖 | 多人同时编辑丢数据；无离线队列 |
| L5 | 后端 JSON 文件存储 | 无法扩展查询/统计；并发弱；无备份恢复 |
| L6 | 无提醒、无导入导出、无统计 | 价值停留在“看课表” |
| L7 | Web 端不落本地存储 | 依赖云同步，无网络时只能看空表 |
| L8 | 单课表 | 学期切换、多份课表场景不支持 |

## 3. 用户画像与典型场景

### 3.1 用户画像

- **大学生（主用户）**：需要按真实校历管理课程，关注单双周、调休、考试周。
- **中小学教师/教务人员**：需要周课表分享给班级群、只读订阅。
- **职场培训/兴趣班学员**：课表简单，但需要多份课表与提醒。

### 3.2 典型场景

- **S1 学期录入**：新学期按教务系统课表逐门录入，支持单双周与起止周；一次录入，整学期可用。
- **S2 多端查看**：手机端课表 + 电脑 Web 端随时查看，数据一致。
- **S3 班级共享**：班长录入班级课表，生成只读订阅链接发到班级群，同学无需注册即可查看。
- **S4 上课提醒**：上课前 10 分钟手机通知，含教室。
- **S5 考试/假期**：考试安排单独录入；节假日与调休自动修正当天是否上课。
- **S6 数据迁移**：旧手机换新手机、重装应用后登录即可恢复全部数据。

## 7. 技术架构改造建议

### 7.1 客户端（KMP）

- **模块拆分**（当前单模块 `composeApp` → 建议按 feature 分层，仍可保持单模块但包结构分层）：
  - `model`：领域模型与序列化
  - `data`：本地仓库 + 云端仓库 + 同步引擎
  - `ui`：页面/组件/主题
  - `platform`：expect/actual（通知、日历导入、系统设置）
- **状态管理**：引入生命周期感知的 ViewModel（`org.jetbrains.androidx.lifecycle:lifecycle-viewmodel-compose`），替代纯 `remember` 状态，避免配置变更/进程重建丢状态。
- **导航**：统一导航方案（Compose Navigation Multiplatform），支持多页面（课表/设置/共享/统计）。
- **本地存储演进**：multiplatform-settings 保留用于轻量配置；课程数据迁移到 SQLDelight（Android/iOS/Desktop）或 DataStore，Web 端用 IndexedDB（经 expect/actual 封装）。
- **通知**：expect/actual 封装本地通知（Android NotificationManager / iOS UNUserNotificationCenter / Desktop 托盘提示）。

### 7.2 后端

- **框架**：当前 JDK HttpServer 适合原型；升级后建议切换 **Ktor Server**（与 Kotlin 技术栈一致、路由/序列化/限流生态成熟），或保留 HttpServer + 自研分层（路由、service、repository）。
- **数据库**：
  - 开发期：SQLite（快速迭代），表结构见第 8 节。
  - 生产：**宝塔 MySQL**（已确认），按 MySQL 建表；ORM 建议 Exposed 或 JDBC，便于切换。
- **登录**：V1.1 不做；V2.0 实现邮箱/手机号+密码（bcrypt + JWT）。微信登录（P1）需企业资质，接入时新增 `POST /auth/wechat`，主体架构预留。
- **鉴权**：注册/登录 → 签发 JWT（access + refresh）；接口统一鉴权中间件。
- **API 规范**：REST + JSON；统一响应结构 `{code, message, data}`；版本前缀 `/api/v1`。
- **部署**：宝塔“Java 项目”或 systemd 常驻；Nginx 反代 `/api`；HTTPS；数据目录与备份脚本。
- **备份**：每日定时备份数据库文件到独立目录/对象存储。

### 7.3 同步引擎设计（核心复杂度）

- 每个实体带 `updatedAt`（毫秒时间戳）与 `deleted` 标记（tombstone）。
- 客户端同步流程：启动拉取 → 本地合并（按实体 id + updatedAt 取新）→ 上传本地变更 → 服务端合并后返回。
- 冲突策略 v1：字段级“后写覆盖 + 保留双方不同课程”；v2（可选）：冲突时用户选择。
- 离线队列：本地写操作先落库并打“dirty”标记，联网后批量推送。

| timetableId | String | 所属课表 | 新增（多课表） |
| updatedAt / deleted | Long / Boolean | 同步元数据 | 新增 |

### 8.2 新增实体

| 实体 | 关键字段 | 用途 |
|------|----------|------|
| User | id, email/phone, passwordHash, createdAt | 账号 |

| SemesterConfig | id, timetableId, startDate, weekCount, holidays[], swapDays[] | 校历/节假日 |

| Exam | id, timetableId, courseId?, name, time, location, note | 考试 |

| SyncMeta | entityId, updatedAt, deleted | 同步元数据 |

### 8.3 数据迁移

- 现有本地 JSON（multiplatform-settings 存储的课程数组）→ 首次升级时导入新表结构。
- 现有云端共享数据（timetables.json）→ 迁移到数据库，并绑定到创建者账号（或迁移工具生成“迁移账号”）。

## 12. 风险与依赖

| 风险 | 等级 | 缓解措施 |
|------|------|----------|
| 同步冲突设计复杂，容易数据丢失 | 高 | v1 采用保守“字段级后写覆盖+tombstone”；冲突可视化提示 |

| 微信登录需企业资质，个人开发者无法开通 | 高 | V1.1/V2.0 先做邮箱/手机号登录；微信登录列 P1 并预留接口，待资质齐备后接入 |
| 现有数据迁移（JSON→数据库） | 中 | 迁移工具 + 迁移前备份 + 灰度 |
| 账号与支付/合规（验证码短信等） | 低 | 验证码服务可选；隐私政策与用户协议 |
| 团队技术栈（KMP wasm 仍较新） | 中 | 保持版本锁定；关键路径先桌面/安卓验证 |
